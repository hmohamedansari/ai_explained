## A condition is not a workflow

A rule answers a local question:

```python
if error_rate > 0.05:
    severity = "high"
```

That is useful, but it does not tell us whether an incident is new, acknowledged, being investigated, waiting for approval, or resolved. That is **state**.

**State is the durable record of where a piece of work is in its lifecycle, plus the facts the system needs to decide what may happen next.** It is not simply a variable that exists while one function runs. Good state survives a retry, a restart and a hand-off to a human.

## Model the work honestly

This is the state machine the Workbench will grow into:

```text
new → triaged → investigating → waiting-for-human → resolved
                       ↓
                    closed-as-noise
```

Each transition needs a reason. When we add transitions, the system should refuse ones that do not make sense: you should not resolve an incident that was never investigated, and you should not investigate one that has been closed.

The current deterministic checkpoint keeps the incident's state in the scenario and shows it in the report. That is deliberate: first make the state visible; then teach the rules that move it.

## Why state is a gift

State gives us three things that are hard to get back later:

- A shared understanding of what is happening now.
- A safe place to resume after a failure.
- A record of why the system did not take some other path.

This becomes important when we add a model. A model call is not the state of the investigation. It is one event inside it.

## Try it

Run the `checkout-regression` scenario and find `State: investigating` in its report. Then run `normal-checkout` and notice that it starts at `triaged`. The route is a decision for this run; the state tells the next part of the workflow where the investigation already is.

## Keep this with you

If a piece of work takes more than one step, write down its states before you ask an LLM to navigate them.
